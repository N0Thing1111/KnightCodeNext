1. A correct route can depend on changing the room

So far, you have planned movements and checked paths. Some rooms need more: a passage is closed until a button is pressed, or a door stays open only while a plate is held. You must reason about how your actions change what can happen next.

The programming idea is state: the facts that describe the situation at a particular moment. In KnightCode, these facts include the knight's position, the crate's position, whether a plate is held, and whether a door is open. State is a useful name for these facts, not a new command to type.

2. Describe the before and after

Imagine an ordinary button that opens a door. Before the knight reaches it, the button has not been activated and the door is closed. After the knight activates it, the door is open. The action changed the state of the room.

  1. Before: door closed; the planned crossing is blocked.
  2. Action: reach and activate the button.
  3. After: door open; the crossing can now be considered.

A condition reads something about the current state. An action may change that state. This means the same question can have a different answer before and after an action. Do not assume an earlier check is still true later.

3. Work out what must happen first

A dependency means one step needs another step to happen first. If crossing a passage requires an open door, and opening the door requires pressing a button, pressing the button must come before crossing.

Plan backwards from the goal: I need to reach the exit. What prevents that? A closed door. What opens it? The button. How do I reach the button? This gives you a useful order instead of a list of unrelated movements.

Then trace forwards to test it. Working backwards helps discover the steps; working forwards checks that each step is possible from the situation left by the previous one.

4. Trace an action followed by a check

For this small example only, suppose one right move activates an ordinary button. Once pressed, it opens the passage directly above the knight's new position. Both movements have been checked against this imagined layout.

KnightCode example - a small practice situation, not a full level solution

move(right)
if can(up):
    move(up)
  1. Move right onto the button. This changes the room.
  2. At the new position, check the upward passage.
  3. If that movement is now possible, move up.

Checking up before the right move would ask about the old position and old room state. Even the same direction name can refer to a different neighboring space after movement. Explain where and when a check happens, not just which word it contains.

5. Distinguish a lasting change from a held condition

  • Ordinary button: once activated, its linked door stays open when the activating object leaves.
  • Pressure plate: its linked door stays open only while an allowed object remains on the plate. When nothing holds it, the door closes.

A pressure plate is not simply an ordinary button with a short timer. What matters is whether it is still held. Standing on a plate can make the door open now without guaranteeing that the door will be open when you reach it.

Ask two different questions: Is the route open at this moment? Will the action I take next keep it open? The second question is what makes the plan reliable.

6. Use a crate to keep a required fact true

The knight pushes a crate by moving toward it. There is no separate push command in these lessons. The crate needs space to move into; a crate blocked against a wall cannot simply be pushed through it.

For a plate that accepts crates, leaving the crate on the plate can keep the door open while the knight leaves. Some switches have different activation rules, so inspect the level rather than assuming every object can activate every switch.

  1. Reach the correct side of the crate.
  2. Push it onto the intended crate-sensitive plate.
  3. Leave it there while the knight takes the opened route.

Throughout the crossing, the required fact is: the plate remains held. You may hear this described as a condition that must stay true. The reasoning matters more than the term. Moving the crate again can undo the useful state.

7. Read and predict a state change

In this thought exercise, one pressure plate controls one door. The plate accepts the knight and crates. At first it is empty. Predict the door after each step: the knight steps onto it; the knight leaves with no crate there; a crate is placed on it; the knight walks away while the crate stays.

Check your reasoning: The door opens when the knight holds the plate, closes when the empty plate is released, opens when the crate holds it, and stays open when the knight leaves but the crate remains. The important fact is occupancy of the plate, not how many times the knight visited it.

Change the assumption: the plate does not respond to crates. Would the last two outcomes still follow?

Check your reasoning: No. The proposed support object must be one the switch accepts. A plan is only as good as the facts it assumes.

8. Find and fix a dependency mistake

A student plans: stand on a pressure plate, walk away from it, then cross its linked door. Nothing else will hold the plate. Explain the first step that breaks the condition needed for crossing.

Check your reasoning: Walking away releases the plate and closes the door. The later crossing fails because the earlier action removed the condition it needed. If a suitable crate and route are available, revise the plan so the crate holds the plate before the knight leaves.

Do not fix this by blindly adding extra movement near the door. The problem is the state of the mechanism, not necessarily the final direction. Trace the cause of the closed door.

9. Plan and explain a multi-step solution

For a room with a crate-sensitive plate and an exit behind its door, write a plain-language plan before choosing movements. Include the side from which to push the crate and the path the knight will take after placing it.

Beside each step, write two short notes: needs and changes. For example: pushing needs a clear destination; pushing changes the crate position. Crossing needs an open door; crossing changes the knight position.

Check your reasoning: A sound plan checks that the crate can reach the plate, the knight can leave it there, and the exit route stays open. Exact movement commands depend on the room. There is no single direction sequence that solves every arrangement.

10. A small connection to real code

Real Python example - read only; not a KnightCode command

plate_held = True
print(plate_held)
plate_held = False
print(plate_held)

This Python example stores a fact using the name plate_held. It first displays True, then changes the stored fact and displays False. This does not operate a real KnightCode door; it is a tiny model of changing information.

The shared logic is tracking state over time. A fact can change, and a later check must use the current situation. You do not need to create variables in the KnightCode terminal to practise that reasoning.

11. Practise with your mechanisms

  • Open the Way: identify the button action that must happen before the crossing.
  • Keep It Open: explain what holds the plate after the knight moves away.
  • Multi-Door Vault: list which mechanism affects which passage, then order the dependencies.

Before running, explain not only where the knight goes but what changes in the room. After running, look for the first state change that differed from your prediction.

12. Check your reasoning

  • Why can a condition have a different answer after a movement?
  • Why is a currently open door not always safe to plan around?
  • What must remain true while crossing a pressure-plate-controlled route?

Check your reasoning: Movement can change position and activate or release mechanisms. An action may close a route that was open a moment ago. The needed plate must remain held by an allowed object until the plan no longer depends on that door.
