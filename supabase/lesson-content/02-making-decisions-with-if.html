1. Move from a fixed plan to a checked action

A sequence tells the knight what to do in order. Sometimes one instruction should run only when something is true. For example, you may want the knight to move right only when movement to the right is possible.

This is a decision. The program checks a question, then uses its answer to decide whether a particular action runs. You still design the plan. A condition gives the program information about the current situation; it does not work out the whole route.

By the end of this lesson, explain both outcomes: what happens when the answer is true, and what happens when it is false.

2. A condition asks; an action changes something

can(right) asks whether the knight can move right from its current position. The answer is true when that movement is possible and false when it is blocked. True and false are the two possible answers to this kind of condition.

move(right) is an action. It attempts movement and may change the knight's position. Checking can(right) does not itself move the knight.

  • Question: can movement happen?
  • Decision: should this group of instructions run?
  • Action: perform the movement when the decision allows it.

Keeping these separate prevents a common mistake: thinking that asking about a direction also sends the knight in that direction.

3. Read a single decision

KnightCode example - a small practice situation, not a full level solution

if can(right):
    move(right)

Read this as: If moving right is possible now, move right. The word if introduces the decision. The condition is can(right). The colon begins the following group of instructions, and the spaces before the move show that it belongs to that group.

That indented group is called a block. Use four spaces in these examples. The layout matters because it shows which instructions depend on the answer. Learn to see the relationship: the movement belongs to the decision.

If the answer is false, the program skips this block. It does not automatically move left, wait for a door, or search for a different route.

4. Trace both possible answers

  1. Right is open: check can(right), obtain true, run the indented move, then continue after the block.
  2. Right is blocked: check can(right), obtain false, skip the indented move, then continue after the block.

In the second case, skipping the move is the correct behavior for these instructions. A skipped block does not mean the whole program has ended. It means that this particular action was not selected.

An if makes one check each time execution reaches it. It does not keep rechecking until movement becomes possible. Rechecking through repetition comes in a later lesson.

5. Decide what belongs inside the block

KnightCode example - a small practice situation, not a full level solution

if can(right):
    move(right)
move(up)

The right move belongs to the decision. The up move lines up with if, so it is outside the block. Provided execution continues, the up move is attempted after either outcome. Assume the upward move is clear from both possible positions in this example.

  1. Right open: move right, then move up.
  2. Right blocked: skip moving right, then move up.

Now imagine indenting the final line by four spaces as well. Both movements would belong to the same decision. When the condition is false, both would be skipped. A small change in grouping can make a large change in the plan.

Also, one successful check of right does not prove that a later move up is safe. A condition only answers the question you asked.

6. Read and predict two situations

Use the program below. In situation A, up is open and left is clear after moving up. In situation B, up is blocked but left is clear at the starting position. Predict the moves in each situation.

KnightCode example - a small practice situation, not a full level solution

if can(up):
    move(up)
move(left)

Check your reasoning: A: the condition is true, so the knight moves up and then left. B: the condition is false, so the knight skips up and moves left from the start. The final left instruction runs in both cases, but it starts from a different position.

What would change if the left movement were inside the block?

Check your reasoning: In B, neither movement would run. In A, both would still run. Trace the false case to see the difference; testing only the true case would miss it.

7. Find the wrong question

A student wants to move up only when up is open. They write:

KnightCode example - a small practice situation, not a full level solution

if can(right):
    move(up)

Does an open path on the right prove that the upward path is open? Imagine right open and up blocked. Then imagine right blocked and up open.

Check your reasoning: No. The question and the intended action do not match. In the first situation the program selects an upward move without checking up. In the second it skips a possible upward move. For the stated goal, change the condition to can(up).

A useful condition must answer a question that matters to the action or plan. Simply adding an if statement does not make a program correct.

8. Plan and write a guarded step

Write a program that attempts one left move only when left is open, then attempts one down move outside that decision. Assume down is clear from either resulting position. Before writing code, say which action depends on the condition and which does not.

KnightCode example - a small practice situation, not a full level solution

if can(left):
    move(left)
move(down)

Compare your answer with this example. Test it in your head with left open and with left blocked. Explain why down is outside the block. This explanation is more important than matching the example character for character.

If down is not known to be safe in a real room, inspect that part of the route or add a suitable check. Do not carry the exercise's assumptions into every level.

9. A small connection to real code

Real Python example - read only; not a KnightCode command

lives = 2
if lives > 0:
    print("Keep playing")
print("Check finished")

Here, lives > 0 asks whether the stored number is greater than zero. With 2 lives, both messages appear. With 0 lives, the first message is skipped and only the final message appears. The number is example data, not a KnightCode command.

The shared logic is conditional execution: some instructions depend on an answer, while instructions outside the block continue afterwards. You are learning that relationship, not a Python spelling test.

10. Apply it to the room, not just one move

  • Check Before Moving: choose a direction on your planned route and explain the question before the guarded move.
  • What If It Is Blocked?: predict a skipped move and describe how the later instructions continue around the obstacle.
  • You Choose the Condition: match each question to the part of the route it should help with.

An open direction is information about movement, not proof that the exit lies that way. Your full sequence must still reach the goal. Before each check, identify the knight's position at that point in the program.

11. Check your reasoning

  • Does can(up) move the knight?
  • When an if condition is false, what happens to its block?
  • Why should you test both true and false situations?
  • Does checking one direction once guarantee that it stays open later?

Check your reasoning: The check asks a question without moving. A false condition skips its block. Testing both answers reveals unwanted moves and unwanted skips. Later movement or changes in the room may change the answer, so a previous result is not a permanent promise.
