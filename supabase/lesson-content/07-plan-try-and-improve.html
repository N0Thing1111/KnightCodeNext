1. Solve the problem before choosing commands

You now have several tools: sequences for order, conditions for decisions, loops for repetition, and state reasoning for changes in the room. This lesson is about choosing and combining them to solve a complete problem.

The target is not a program containing every command. The target is a plan you can explain: what must happen, why the steps are possible, how the program chooses or repeats them, and how you know the goal is reached.

A clear short sequence can be better than an unnecessary loop. A condition is useful when the plan needs a check, not simply because the command is available.

2. Understand the room as a set of facts

Before typing, identify the start, exit, blocked passages, mechanisms and movable objects. Separate what you know from what you still need to test. For example, a wall-looking panel may not behave like a solid wall.

  • Goal: what must be true when the solution finishes?
  • Available actions: what can the knight do with the commands taught so far?
  • Constraints: which passages are blocked, and which objects must remain in place?
  • Unknowns: which movement or mechanism behavior needs checking?

An assumption is something the plan takes as true. State it explicitly. "The crate can be pushed onto the plate from this side" is an assumption you can inspect and test.

3. Break the goal into smaller goals

Dividing a problem into manageable parts is called decomposition. For an exit controlled by a crate-sensitive plate, the smaller goals might be:

  1. Reach the side of the crate needed for the push.
  2. Place the crate on the correct plate.
  3. Leave the crate there and reach the opened passage.
  4. Cross the passage and reach the exit.

These parts are connected. The second needs a reachable pushing position. The third needs the plate held. The last needs the door open. Write these dependencies before translating the plan into directions.

After each part, describe the expected state: knight position, crate position and door status. Those checkpoints help you locate a mistake later.

4. Choose the structure that fits each part

  • Sequence: several different actions must happen in a specific order.
  • If or if/else: the next action depends on a true-or-false answer.
  • Repeat: a known action group occurs a known number of times.
  • While: keep performing a group while a condition remains true.

A complete room can use several of these, but it does not have to use all of them. Explain the reason for each structure you choose. "I used repeat because this same pair occurs twice" is a reason. "I used repeat because the lesson mentions it" is not enough.

5. Trace a combined program

For this practice example, assume two right moves are clear. After them, up is open; right remains open after moving up. No goal ends the program early. Predict the full route:

KnightCode example - a small practice situation, not a full level solution

repeat(2):
    move(right)
if can(up):
    move(up)
else:
    move(down)
move(right)
  1. The loop performs right twice, changing the starting position for the decision.
  2. The upward check is true in the stated situation, so up runs and down is skipped.
  3. The final right move is outside the decision, so it runs afterwards.

Check your reasoning: The action sequence is right, right, up, right. If up were blocked after the loop and down were clear, the sequence would instead be right, right, down, right. The final right move would also need to be possible from that alternate position.

This is a small example of combining structures, not a full solution for your final game room. Map each part of your actual plan to the actual layout.

6. Test a prediction, not just a final score

Before Run, write an expected result at each checkpoint. During the run, observe what actually happens. Afterwards, compare the two. A failed attempt is useful when it gives you evidence about which assumption or instruction was wrong.

A simple test note can be: expected the crate to stay on the plate; observed it move off during the last push; therefore the door closed before the crossing. This explanation points to a specific correction.

Also check starting conditions. A retry from a changed room may not be comparable to an earlier attempt. If you want to compare two program versions, make sure they start from the same intended setup.

7. Find the first mismatch

Debugging means locating and correcting the cause of unwanted behavior. Start with the earliest point where your prediction and the actual run differ, not merely the place where the knight finally gets stuck.

  • Was the instruction understood? Check command spelling and grouping if execution cannot begin.
  • Did the selected action match the plan? Check directions and branch choices.
  • Did a repeated group run too often or include a one-time action?
  • Did an earlier action remove a condition needed later, such as a held plate?

Change one relevant part, predict its effect, and test again. Changing several unrelated things at once makes it harder to explain which change helped.

8. Find and fix a combined logic mistake

The intended route is two right moves, then one upward move only if up is possible. A student writes:

KnightCode example - a small practice situation, not a full level solution

repeat(2):
    move(right)
    if can(up):
        move(up)

Assume up is open after each right move. Expand the program. Does it match the intention?

Check your reasoning: It produces right, up, right, up. The decision belongs to the repeated body, so it is reached twice. Move the whole if block outside repeat, keeping its move indented under if. The corrected structure is shown below.

KnightCode example - a small practice situation, not a full level solution

repeat(2):
    move(right)
if can(up):
    move(up)

The correction changes when the decision happens. Explain that relationship rather than saying only that some spaces were removed.

9. Improve only after preserving correctness

Suppose a working sequence contains right, up, right, up. Replacing it with repeat(2) around right and up can make the repeated pattern clearer. Verify it by expanding the new version and comparing the ordered actions.

Do not assume that fewer written lines always mean fewer attempts, less movement, or a better route. These are different measures. A useful improvement either makes the plan easier to understand or improves a chosen result while still reaching the goal correctly.

For a mechanism puzzle, also compare state changes. A route that reaches the same position but releases a necessary plate is not equivalent to one that keeps it held.

10. A small connection to real code

Real Python example - read only; not a KnightCode command

total = 0
for value in [2, 4, 1]:
    if value > 1:
        total = total + value
print(total)

This Python example visits three numbers in order. It adds a number only if it is greater than 1. Starting at 0, the total becomes 2, then 6, then stays 6 when 1 is skipped. The final display is 6.

The names hold information, the loop repeats, the condition chooses, and the addition changes the state. The same tracing method works outside the game. You are not expected to learn Python lists here; follow the stated three values and explain each decision.

11. Build and explain your own room solution

  1. State the goal and important starting facts.
  2. Write smaller goals and the order they depend on.
  3. Choose movements, decisions or loops for each part.
  4. Predict position and mechanism state at checkpoints.
  5. Run, compare, and identify the first mismatch.
  6. Correct the cause and explain why the revision helps.

In Find and Fix, check whether the plate is held before the plan depends on its door. In Your KnightCode Challenge, combine the repeated approach, crate placement and exit route according to the room you see. Avoid copying a practice snippet as if it were the whole answer.

12. Show that you understand the logic

After solving a room, explain your program to someone who cannot see your code. Include why each decision is needed, what each loop repeats, what stops it, and which facts must remain true.

  • If a path became blocked, which part of your plan would need reconsidering?
  • Which test showed you the first mistake?
  • What did you change, and why did that change address the cause?
  • Can you describe the same plan in plain words without the game command spelling?

Check your reasoning: A strong explanation connects actions to results and evidence to corrections. Reaching the exit demonstrates one successful run. Explaining the plan, its assumptions and its limits shows the programming logic behind that run.
