1. Find a pattern before choosing a loop

Some routes contain the same action or group of actions several times. A loop is a way to repeat a group without writing that group out each time. This lesson uses repeat when the number of repetitions is known.

The goal is not to make every program as short as possible. The goal is to recognize a pattern, express it clearly, and keep the intended behavior. A shorter program that takes the wrong route is not an improvement.

First describe the complete route. Then ask: which part is exactly repeated, and how many copies of that part are needed?

2. Replace repeated instructions with a count

KnightCode example - a small practice situation, not a full level solution

move(right)
move(right)
move(right)

Assume all three movements are possible and the level does not end during them. This sequence performs the same action three times. We can express that repeated part as:

KnightCode example - a small practice situation, not a full level solution

repeat(3):
    move(right)

The number 3 is the repetition count. The indented line is the loop body: the instruction that runs on each repetition. After the third repetition, execution continues after the loop.

The knight still performs three moves. The loop saves repeated writing, not physical movement. It also does not automatically check whether a wall is in the way.

3. Expand the loop to check your reasoning

One pass through the body is called an iteration, or simply a repetition. Trace repeat(3) by numbering the passes:

  1. First repetition: run move(right).
  2. Second repetition: run move(right) again, from the new position.
  3. Third repetition: run move(right) again, then finish the loop.

To check a loop, mentally replace it with the full sequence it represents. If that expanded sequence does not match the route, the loop does not match either. This is a useful way to test your logic without relying on how compact the code looks.

In the game, a level finishing or a program being stopped can end execution early. The trace here describes normal completion of the example.

4. A repeated group can contain more than one action

KnightCode example - a small practice situation, not a full level solution

repeat(2):
    move(right)
    move(up)

Both indented instructions belong to the body. Each repetition performs right and then up. The expanded order is right, up, right, up. It is not right, right, up, up.

Two repetitions of a two-action body produce four movement actions. Keep these quantities separate: number of passes and number of actions inside each pass.

A block is repeated as a unit, but instructions within it still run in order. A loop does not remove the sequence rules you already learned.

5. Place one-time actions outside the loop

Imagine a clear route requiring three right movements and then one up movement. The turn should happen once, after the repeated section.

KnightCode example - a small practice situation, not a full level solution

repeat(3):
    move(right)
move(up)

Because up lines up with repeat, it is outside the loop. The route is right, right, right, up. If you indent up inside the body, the route becomes right, up, right, up, right, up. That describes a different pattern.

Before writing a loop, label each part of your plan as repeated or once afterwards. Indentation should reflect that decision.

6. Read and predict the full sequence

Assume every move is possible. Write the expanded sequence and count the movements before reading the answer.

KnightCode example - a small practice situation, not a full level solution

repeat(2):
    move(up)
    move(right)
move(down)

Check your reasoning: The sequence is up, right, up, right, down: five movement actions. The body contributes four actions across two repetitions. Down contributes one more after the loop. The final position is two movements right and one up from the start in this open-area example.

What changes if the count becomes 3?

Check your reasoning: The pair runs three times, producing six body movements, then down runs once: seven movements in total. The change affects the whole repeated group, not just its first line.

7. Find and fix a misplaced turn

The intention is right, right, right, then up once. A student writes:

KnightCode example - a small practice situation, not a full level solution

repeat(3):
    move(right)
    move(up)

Which part of the written program makes the route disagree with the intention? Expand it rather than guessing a different count.

Check your reasoning: The up move is inside the repeated body, so it happens three times. Move that line outside the block. Changing only the repetition count cannot produce three right moves and one up move from this two-action body.

This is a grouping mistake. Other loop mistakes involve the wrong count or the wrong action. Identify which kind of mismatch you have before editing.

8. Plan and write a repeated pattern

For an open practice route, express left, down, left, down, left, down, then right once using a loop. Name the smallest repeated group before you write it.

KnightCode example - a small practice situation, not a full level solution

repeat(3):
    move(left)
    move(down)
move(right)

Check your reasoning: The repeated group is left followed by down. It occurs three times. Right is outside the loop because it happens once afterwards. There are seven movement actions in the expanded plan.

Now imagine an obstacle blocks the second downward move. The pattern is easy to describe, but it no longer gives a clear route. A repeat count is a plan, not proof that all its actions can succeed. Check each repetition at its new position.

9. Decide whether a fixed count is appropriate

Use repeat when you know both the body and the required count. A measured three-step section is a good candidate. A route where you only know "keep going until movement is blocked" needs a different kind of reasoning, which the next lesson introduces.

Two programs can also be equally clear without both using loops. A short sequence of unrelated turns may be easier to explain directly. Do not force different actions into a pattern that is not really there.

When you claim that two versions are equivalent, explain that they perform the same ordered actions under the same starting conditions. Comparing line counts alone is not enough.

10. A small connection to real code

Real Python example - read only; not a KnightCode command

for step in range(3):
    print("Check the next item")
print("Finished")

This Python loop displays the first message three times, then displays Finished once. The name step is used by Python to track the repetitions; you do not need to use it inside this example.

The shared idea is a fixed number of passes through a block. Python writes that idea differently from KnightCode. Focus on what repeats, how often, and what happens afterwards, rather than memorizing the language form.

11. Use repetition in your levels

  • Do It Again: find the right-and-up pattern, count its repetitions, and trace the position after each pair.
  • Repeat, Then Turn: separate the repeated approach from the turn, button action and remaining route.

Before Run, expand the loop aloud or on paper. After Run, compare the movement pattern. If it differs, inspect the body and count separately. A loop that finishes is not necessarily a loop that reaches the goal.

12. Check your reasoning

  • What is the difference between a repetition and a movement action?
  • Why does moving a line outside a loop change how often it runs?
  • Does shorter code always mean fewer game movements?

Check your reasoning: One repetition runs the entire body, which may contain several actions. An outside line runs after the loop rather than on each pass. A loop can shorten the written program while keeping exactly the same movement sequence.
